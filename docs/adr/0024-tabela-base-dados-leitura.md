# ADR 0024 — Nova tabela `base_dados_leitura`

## Contexto

Usuário forneceu uma planilha (`C:\Users\joaow\Desktop\base_dados_leitura.xlsx`), só com
cabeçalho, sem linha de dado, e pediu pra criar a tabela correspondente no Supabase local.

## Decisão

### Estrutura: réplica exata de `control_empreiteiras`

O cabeçalho da planilha (23 colunas: `concessionaria, empreiteira, equipe, nome_do_usuario,
mes_ref_livro, data_da_leitura, hora_da_leitura, unidade_consumidora, codigo_da_localidade,
descricao_da_localidade, tipo_de_localizacao_da_uc, etapa, livro, status_releitura, equipamento,
especificacao, mensagem, mensagem_auxiliar, observacao_de_campo, status_foto,
faturamento_em_campo, status_impressao_do_comunicado, forma_de_entrega`) bate **exatamente**,
mesmos nomes e mesma ordem, com a tabela `control_empreiteiras` que já existe no banco. Sem
linha de dado pra decidir tipos diferente, replicados os mesmos tipos de `control_empreiteiras`
(a maioria `character varying(255)`, exceto `mensagem`/`mensagem_auxiliar`/
`observacao_de_campo` como `text`) em vez do padrão genérico "tudo varchar(255)" usado quando
não existe nenhum precedente — aqui existe um precedente exato, mais confiável que o genérico.

### RLS/multi-tenant: réplica exata do padrão do projeto

`empresa_id uuid not null references empresas(id)` + RLS enable/force + a mesma policy já usada
em toda tabela de negócio (ADR 0009 — sem exceção pra tabela de referência). Índices em
`empresa_id`, `livro` e `mes_ref_livro`, mesmo conjunto de `control_empreiteiras`.

```sql
CREATE TABLE public.base_dados_leitura (
  concessionaria character varying(255),
  ...
  mensagem text,
  mensagem_auxiliar text,
  observacao_de_campo text,
  ...
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  empresa_id uuid NOT NULL REFERENCES public.empresas(id)
);
```

Aplicado direto via `docker exec supabase-db psql` (sem framework de migration neste projeto,
mesmo caminho da ADR 0021 Adendo 2).

### Fora de escopo desta tarefa

Só a criação da tabela foi pedida — não foi wireada nenhuma importação (nem em
`BACKEND/src/config/importacaoConfig.js`, nem nenhum endpoint novo). Se o usuário quiser
importar dado pra essa tabela pela aba Importação, é um pedido separado (mesmo padrão da ADR
0021: `coordenadas_ucs_mineradas` foi criada primeiro, ganhou importação só num Adendo
posterior).

## Verificação

- `\d base_dados_leitura` confirma 23 colunas + `id` + `empresa_id`, tipos batendo com
  `control_empreiteiras`, RLS forçado, 1 policy, 3 índices, FK pra `empresas`
- Sanidade de RLS: sessão sem `app.nivel`/`app.empresa_id` setados devolve 0 linhas
  (fail-closed)

## Adendo 1 — Importação habilitada na aba Importação

Usuário pediu, na sequência: habilitar a importação dessa tabela pela aba Importação, e
confirmou a dúvida sobre o `id` — sim, `id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
já tinha sido criado junto com a tabela original (não é um passo separado).

Nova entrada em `BACKEND/src/config/importacaoConfig.js` (`base_dados_leitura`), idêntica à de
`control_empreiteiras` (mesmo `modo: 'upsert'`, mesma `chave: ['data_da_leitura',
'hora_da_leitura', 'nome_do_usuario', 'unidade_consumidora']`, mesma lista de `colunas`) — sem
mudança nenhuma no motor de import genérico (`importacaoService.js`), a aba/endpoint/dropdown do
frontend já são inteiramente orientados por essa configuração (`GET /importacao` deriva a lista
de `Object.keys(CONFIG_IMPORTACAO)`).

Testado ponta a ponta: workbook `.xlsx` de 1 linha gerado em memória (mesmas 23 colunas),
importado via `importarArquivo()` dentro de uma transação com `ROLLBACK` (mesmo padrão da ADR
0021 Adendo 3 — não grava nada de verdade), linha confirmada gravada corretamente dentro da
transação, e confirmado que o `ROLLBACK` não deixou rastro (`SELECT count(*)` = 0 depois).
`npm test` (12/12) continua passando.
