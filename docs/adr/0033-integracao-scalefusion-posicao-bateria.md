# ADR 0033 — Coleta de posição/bateria via API Scalefusion (nova tabela `scalefusion`)

## Contexto

Usuário quer localizar em tempo real os colaboradores (inicialmente focado em pedestres — os
motoqueiros ficam pra quando a integração com a API de frota SEGSAT tiver o mapeamento
placa↔colaborador resolvido, ver conversa anterior nesta sessão) e também exibir nível de bateria
do aparelho de cada um. Forneceu um documento de especificação técnica (produzido pela A2L
Engenharia, `Especificacao_API_Scalefusion_COPEL.docx`) descrevendo uma interface que a FIMM
disponibiliza sobre o Scalefusion (MDM — Mobile Device Management) usado nos aparelhos de campo da
Copel, e na sequência a URL base + token de acesso.

### O que a API entrega (confirmado ao vivo, não só lido do documento)

- `GET /devices` (bearer token simples, sem fluxo de login/sessão — token não expira) devolve os
  424 aparelhos da conta de uma vez, sem filtro nem paginação. Cada um: `id` (uso interno do
  Scalefusion), `name` (formato `PREFIXO - COLABORADOR - IMEI`), `battery_status` (0-100),
  `battery_charging` (bool), `location.lat/lng/address/date_time` (não garantido pelo contrato
  OpenAPI, mas presente na prática).
- **O nome do colaborador já vem embutido no campo `name`** — diferente da API SEGSAT (frota de
  veículos), aqui não existe o problema de "não sei quem dirige o quê": o nome está no próprio
  dispositivo. Confirmado ao vivo: de 424 dispositivos, 416 têm nome no formato esperado, e desses
  300 batem por igualdade exata (maiúsculas) com `ativos_inativos.colaborador`. Os que não batem em
  geral são gente que já saiu da empresa ou aparelho de uso compartilhado (ex.: "BASE UMUARAMA").
- Resposta cacheada 5min no lado do servidor deles — consultar mais rápido que isso não traz dado
  novo (documento já recomenda coleta a cada 5min pra formar histórico próprio, dado que a API não
  guarda histórico nenhum).
- `POST /alert` manda mensagem pro aparelho — **fora do escopo desta rodada**, usuário pediu
  explicitamente pra não mexer nisso agora.

## Decisão

### Nova tabela `scalefusion` — histórico completo, não só "última posição"

Usuário pediu explicitamente rastreabilidade do dia (posição E bateria ao longo do tempo, não só o
retrato mais recente) — cada coleta bem-sucedida vira uma linha nova, nunca um upsert. Estrutura
(mesmo padrão de toda tabela de negócio do projeto — `id bigint identity` + `empresa_id uuid` com
RLS `isolamento_empresa` idêntica às demais, aplicada via `docker exec supabase-db psql` como de
costume, sem framework de migration):

```sql
CREATE TABLE public.scalefusion (
  device_id bigint,
  nome_dispositivo character varying(255),
  colaborador character varying(255) NOT NULL,
  cargo character varying(255),
  bateria_percentual smallint,
  bateria_carregando boolean,
  latitude character varying(255),
  longitude character varying(255),
  endereco text,
  data_hora_posicao timestamptz,
  coletado_em timestamptz NOT NULL DEFAULT now(),
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  empresa_id uuid NOT NULL REFERENCES public.empresas(id)
);
```

`latitude`/`longitude` como texto (não `numeric`) — mesma convenção já usada em
`coordenadas_ucs_mineradas`, consumida com `Number(...)` no ponto de uso, não no banco.
`data_hora_posicao` é `timestamptz` de verdade (não texto DD/MM/YYYY como nas tabelas do scraper
Copel) — a API já entrega epoch em milissegundos, não precisa do tratamento de formato texto que as
outras integrações exigem. `cargo` denormalizado do roster no momento da coleta — evita join toda
vez que uma tela quiser separar pedestre/motociclista.

### Só grava colaborador que bate com o cadastro (`ativos_inativos`)

Dispositivo sem correspondência em `ativos_inativos` (nome fora do padrão, ex-funcionário, aparelho
compartilhado) não vira linha na tabela — decisão de manter o volume de dado ligado só a
colaboradores de verdade, já que é isso que foi pedido ("rastreabilidade do dia do colaborador").
Se um dia for útil auditar o parque inteiro (não só quem bate com o cadastro), isso é um pedido
separado — não foi construído aqui pra não sujar a tabela de "posição real de colaborador" com
"inventário de aparelho".

### Dedup por posição, não por tempo

Antes de gravar, compara `data_hora_posicao` do dispositivo com a ÚLTIMA linha já gravada daquele
colaborador (qualquer dia) — se for a mesma, não grava de novo. A API só atualiza a cada 5min
mesmo; rodar o job também a cada 5min ainda pode pegar o retrato repetido se o aparelho não andou
ou não reportou desde a última coleta. Sem esse corte, a tabela cresceria com linhas idênticas
sempre que alguém ficasse parado.

### Job de coleta contínua — mesmo padrão dos scrapers Copel

`scalefusionJob.js` replica exatamente a estrutura de `coletaMassivasJob.js` (loop
contínuo + watchdog de 2min + trava contra execução concorrente), só que com pausa de 5min entre
ciclos (não 5s) — alinhado ao TTL do cache da própria API, chamar mais rápido não adianta.
`iniciarJobScalefusion()` não inicia se `SCALEFUSION_API_TOKEN` não estiver no `.env` (log de aviso,
não erro fatal — não impede o resto do servidor de subir).

### Fora de escopo desta rodada (decisão explícita do usuário)

- `POST /alert` (envio de mensagem) — nada construído, nem endpoint nem tela.
- Exibição no mapa/frontend — só a coleta e o armazenamento foram pedidos nesta rodada. Falta
  decidir como/se isso substitui o ícone de "último ponto" do colaborador no mapa (ver Adendo 10 da
  ADR 0030) — próxima conversa.
- Limpeza dos 5-8 cadastros fora do padrão no Scalefusion — depende da FIMM/COPEL, fora do alcance
  deste código.

## Consequências

- Tabela cresce ~1 linha por colaborador a cada 5min em que ele de fato se move (não uma linha fixa
  por ciclo) — bem mais devagar que "424 × 288/dia" do pior caso, já que a maior parte do parque
  não bate com o cadastro e o dedup corta posição repetida.
- Token do Scalefusion (sem expiração, conforme a própria especificação) guardado só em `.env`
  (`SCALEFUSION_API_TOKEN`), nunca commitado — `.env.example` documenta a variável sem o valor.
- Nome do colaborador aqui é por CASAMENTO DE STRING EXATO (maiúsculas) contra `ativos_inativos` —
  mesma fragilidade que já existe no resto do projeto (ex.: `contr_execucao_leitura.colaborador` x
  `base_dados_leitura.nome_do_usuario`): erro de digitação num dos dois lados faz o colaborador
  ficar de fora silenciosamente. Não é um problema novo introduzido aqui, é o mesmo padrão já
  aceito em todo o sistema.

## Verificação

- Chamada real à API (`GET /devices`) com o token fornecido: 424 dispositivos, formato batendo com
  a especificação.
- `coletarPosicoes()` rodado contra o banco real: 424 dispositivos processados, ~300 batendo com
  `ativos_inativos`, gravação incremental confirmada (rodadas sucessivas só acrescentam posição
  quando `data_hora_posicao` muda — 285 colaboradores distintos, a maioria com 1 linha, alguns com
  2-3 de coletas sucessivas do job já rodando em produção via nodemon).
- `\d+ scalefusion` confirma RLS forçada com a mesma policy `isolamento_empresa` de toda tabela do
  projeto.
- `BACKEND/test/isolamento_tenant.test.js` ganhou `scalefusion` na lista de tabelas testadas
  (fail-closed + isolamento cross-empresa) — suíte completa (14 testes) passa.

## Adendo 1 (2026-09-06) — posição real do pedestre no mapa; bateria na lista lateral

Dois pedidos na sequência, ambos usando o que já estava coletado:

- **Mapa**: só o PEDESTRE (`!ehMoto`) passa a usar a posição do Scalefusion em vez da última UC
  realizada — motoqueiro fica como estava até a integração de frota (SEGSAT) resolver o mapeamento
  placa↔colaborador (ver conversa anterior desta sessão). Novo endpoint `GET
  /colaboradores/scalefusion` (`obterUltimasPosicoes` em `scalefusionService.js` — `DISTINCT ON
  (colaborador)` pegando a linha mais recente de cada um) alimenta um novo signal
  `scalefusionPorColaborador` no frontend, recarregado a cada 60s (mesmo intervalo de
  atividade/localizações, mas SEM depender de `filtroData` — Scalefusion não tem conceito de "dia
  passado", é sempre o retrato mais recente já coletado).

  `atualizarMarcadoresColaboradores()` (`mapa-bases.ts`) passa a iterar sobre a UNIÃO dos nomes de
  `localizacoes()` (leitura) e `scalefusionPorColaborador()` (posição real) — um pedestre pode ter
  uma sem ter a outra (contratado recente sem UC ainda; ou aparelho sem correspondência no
  Scalefusion). Posição real só é usada se tiver menos de 24h de idade
  (`LIMITE_POSICAO_REAL_MS`) — sem esse corte, um aparelho que parasse de reportar ficaria marcado
  como "tempo real" pra sempre (mesma preocupação já registrada na especificação da API sobre
  "idade da última posição"); passando disso, cai de volta pra última UC realizada, mesmo
  comportamento de antes.

- **Bateria na lista lateral**: ícone + percentual ao lado do nome, pra motoqueiro E pedestre (sem
  filtro de cargo — qualquer colaborador com dado no Scalefusion mostra), usando o mesmo
  `scalefusionPorColaborador`. Cor por faixa (vermelho ≤20%, âmbar ≤50%, verde acima) — mesmos
  limiares usados em qualquer indicador de bateria comum, não inventados pro projeto.

### Verificação

`obterUltimasPosicoes()` testado direto contra o banco real: 285 colaboradores com posição+bateria
retornados. `tsc --noEmit` e `ng build --configuration production` sem erro (só os warnings
pré-existentes de bundle/leaflet). Não verificado dentro do app de verdade nesta sessão (sem
credencial de teste) — usuário vai confirmar do lado dele.
