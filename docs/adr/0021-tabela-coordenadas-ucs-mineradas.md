# ADR 0021 — Nova tabela `coordenadas_ucs_mineradas`

## Contexto

Usuário forneceu um CSV (`C:\Users\joaow\Desktop\coordenadas_ucs_mineradas.csv`) só com
cabeçalho, sem linhas de dado, e pediu pra criar a tabela correspondente. Colunas do CSV:
`unidade_consumidora, regiao, cod_local, nom_municipio, localidade, endereco, tipo_logradouro,
logradouro, numero_imovel, zona, classe_principal, etapa, livro, sequencia, situacao_uc,
latitude, longitude, coord_confirmada, geom, geom_area`.

Sem linha de dado, não havia como confirmar tipos a partir do conteúdo — nomes sugerem uma
extração/mineração de coordenadas de UC (unidade consumidora) cruzada com endereço/logradouro e
geometria (`geom`/`geom_area`, nomes típicos de coluna PostGIS: ponto e área).

## Decisão

### Tipos de coluna: tudo `character varying(255)`, seguindo o padrão já usado no projeto

Confirmado antes de criar: **PostGIS não está instalado** neste banco
(`SELECT extname FROM pg_extension WHERE extname='postgis'` vazio) — `geom`/`geom_area` não
podem ser um tipo `geometry` de verdade. E o próprio projeto já tem precedente pra dado
geográfico: `tab_ligacao_coordenadas.latitude`/`longitude` são `character varying(255)`, não
`numeric`/`double precision` — o padrão aqui é gravar tudo como texto e converter em tempo de
leitura na aplicação, não confiar em tipo de coluna pra isso. Sem dado de exemplo pra decidir
diferente, replicado o mesmo padrão pra todas as 20 colunas do CSV: `character varying(255)`,
nullable.

### RLS/multi-tenant: réplica exata do padrão de `cidades_localidades`

Toda tabela de negócio deste projeto tem `empresa_id uuid not null references empresas(id)` e
RLS obrigatório (ver skill `/modelo-acesso`, já seguido por todas as tabelas existentes:
`contr_execucao_leitura`, `cidades_localidades`, `calendario_leitura`,
`tab_ligacao_coordenadas`). Inspecionado `cidades_localidades` (DDL, policy, grants, índice) e
replicado igual:

```sql
CREATE TABLE public.coordenadas_ucs_mineradas (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  unidade_consumidora character varying(255),
  regiao character varying(255),
  cod_local character varying(255),
  nom_municipio character varying(255),
  localidade character varying(255),
  endereco character varying(255),
  tipo_logradouro character varying(255),
  logradouro character varying(255),
  numero_imovel character varying(255),
  zona character varying(255),
  classe_principal character varying(255),
  etapa character varying(255),
  livro character varying(255),
  sequencia character varying(255),
  situacao_uc character varying(255),
  latitude character varying(255),
  longitude character varying(255),
  coord_confirmada character varying(255),
  geom character varying(255),
  geom_area character varying(255),
  empresa_id uuid NOT NULL REFERENCES empresas(id)
);

CREATE INDEX idx_coordenadas_ucs_mineradas_empresa_id
  ON public.coordenadas_ucs_mineradas USING btree (empresa_id);

ALTER TABLE public.coordenadas_ucs_mineradas ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.coordenadas_ucs_mineradas FORCE ROW LEVEL SECURITY;

CREATE POLICY isolamento_empresa ON public.coordenadas_ucs_mineradas
  USING (
    ((SELECT current_setting('app.nivel', true)) = 'ROOT')
    OR (empresa_id = ((SELECT NULLIF(current_setting('app.empresa_id', true), '')))::uuid)
  )
  WITH CHECK (
    ((SELECT current_setting('app.nivel', true)) = 'ROOT')
    OR (empresa_id = ((SELECT NULLIF(current_setting('app.empresa_id', true), '')))::uuid)
  );

GRANT INSERT, SELECT, UPDATE, DELETE ON public.coordenadas_ucs_mineradas TO app_user;
```

`(select current_setting(...))` embrulhado em subselect (não a chamada de função solta) — mesmo
cuidado de performance já usado nas outras policies deste projeto (avaliado uma vez como
InitPlan, não por linha).

### Como a DDL foi executada

`app_user` (usuário da aplicação) não é dono de tabela — mesmo padrão de todo DDL deste
projeto. Rodado como `postgres`, via `docker exec supabase-db psql -U postgres -d postgres`
(WSL — o container roda dentro da distro Linux, não é visível direto do Git Bash do Windows).

### Fora de escopo

- **Nenhum código de aplicação foi escrito** — não existe rota/controller/service pra
  `coordenadas_ucs_mineradas` ainda. Usuário só pediu a tabela; import/consulta ficam pra
  quando ele indicar o fluxo (provavelmente uma importação de planilha, no padrão de
  `importacaoConfig.js`/`importacaoService.js`, dado o nome "mineradas" sugerindo dado extraído
  em lote de outra fonte).
- **`geom`/`geom_area` como texto plano**, não um tipo geométrico de verdade — se o uso futuro
  precisar de operação espacial real (distância, contém, interseção), vai exigir instalar a
  extensão PostGIS e migrar a coluna, não só reaproveitar o texto.

## Verificação

Colunas, tipos, índice, RLS (`relrowsecurity`/`relforcerowsecurity` = true) e a policy
`isolamento_empresa` conferidos direto no banco depois da criação — idênticos ao padrão de
`cidades_localidades`.

## Adendo — `id` já era auto-incremento; PostGIS instalado

Usuário pediu dois ajustes depois da criação:

1. **Coluna `id` auto-incremento** — já existia desde a criação original:
   `generated by default as identity`, o equivalente moderno de `SERIAL`/`bigserial` (mesmo
   padrão de `cidades_localidades`, ver corpo desta ADR). Nada mudou, só confirmado.
2. **Instalar PostGIS** — estava disponível na imagem (`pg_available_extensions`, versão
   `3.3.7`) mas não instalado (era exatamente a limitação registrada acima, que forçou
   `geom`/`geom_area` a virar `varchar(255)`). Instalado com
   `CREATE EXTENSION IF NOT EXISTS postgis;` (como `postgres`, mesmo caminho via
   `docker exec supabase-db` da criação original). Confirmado via `PostGIS_Version()`:
   `3.3 USE_GEOS=1 USE_PROJ=1 USE_STATS=1` — GEOS e PROJ ativos, operações espaciais completas
   disponíveis (distância, interseção, contém, transformação de SRID etc.), não só o tipo de
   dado.

**Não convertido**: `geom`/`geom_area` continuam `varchar(255)` — o usuário pediu só pra
instalar a extensão, não pra migrar as colunas. Com a tabela ainda vazia, migrar pra
`geometry(Point, 4326)`/`geometry(Polygon, 4326)` (ou o SRID que fizer sentido pro dado de
origem) fica barato a qualquer momento — é só um `ALTER COLUMN ... TYPE geometry USING
ST_GeomFromText(...)` sem risco de perda de dado real, mas isso é uma decisão de modelagem
(formato de entrada do CSV, SRID) que fica pra quando o usuário indicar o fluxo de import.

## Adendo 2 — importação de 4,1 milhões de registros: `geom`/`geom_area` viraram `geometry` de verdade

Usuário indicou o arquivo real de import
(`C:\Users\joaow\Desktop\WESLEY\PESSOAL\projeto A2L\coordenadas_ligacoes_copel_fimm.csv`,
2,79 GB, 4.120.347 linhas de dado) e pediu pra importar na tabela.

### `varchar(255)` não era só subótimo — não cabia o dado real

As amostras de `geom_area` (WKB hexadecimal de um polígono, ~13 pontos por anel) passam de
400 caracteres — mais que o limite de `varchar(255)`. Import direto teria falhado com "value
too long for type character varying(255)". Como o dado já é EWKB hexadecimal de verdade
(prefixo `0101000020E6100000...` = Point SRID 4326; `0103000020E6100000...` = Polygon SRID
4326 — confirmado por amostragem no início, meio e fim do arquivo: 100% consistente, sem
variação de tipo), a correção certa não era só alargar a coluna — era migrar pro tipo
`geometry` de verdade, exatamente o que o Adendo 1 já tinha preparado o terreno pra fazer (essa
é a razão de o usuário ter pedido pra instalar o PostGIS no pedido anterior).

```sql
ALTER TABLE public.coordenadas_ucs_mineradas
  ALTER COLUMN geom TYPE geometry(Point, 4326) USING ST_GeomFromEWKB(decode(geom, 'hex')),
  ALTER COLUMN geom_area TYPE geometry(Polygon, 4326) USING ST_GeomFromEWKB(decode(geom_area, 'hex'));

CREATE INDEX idx_coordenadas_ucs_mineradas_geom ON public.coordenadas_ucs_mineradas USING GIST (geom);
CREATE INDEX idx_coordenadas_ucs_mineradas_geom_area ON public.coordenadas_ucs_mineradas USING GIST (geom_area);
```

Tabela ainda vazia nesse ponto — `USING` incluído por correção (documenta a conversão real,
caso a tabela algum dia precise ser recriada a partir de um dump em texto), mas não processou
linha nenhuma de fato.

### `empresa_id`: default temporário, removido depois do import

O CSV não tem coluna de tenant — só existe uma empresa cadastrada
(`00000000-0000-0000-0000-000000000001`, "Operação principal (Copel/FIMM)", nome batendo com o
próprio nome do arquivo). `ALTER COLUMN empresa_id SET DEFAULT '00000...001'` antes do import
(pra a coluna ser preenchida sem precisar listá-la no `COPY`), removido com `DROP DEFAULT`
logo depois — evita que uma inserção futura sem `empresa_id` explícito caia silenciosamente
nessa empresa por engano.

### Caminho de execução: `\copy` do lado do host WSL, não `docker exec`

RLS está com `FORCE ROW LEVEL SECURITY` (Adendo 1) — mesmo como `postgres` (dono da tabela),
um `COPY` broto teria sido bloqueado pela policy sem `app.nivel = 'ROOT'` setado na sessão.
`SET app.nivel = 'ROOT';` antes do `\copy` resolve isso.

O arquivo está no disco Windows (`C:\Users\...`), fora do container. `\copy` (comando de
cliente do `psql`, diferente do `COPY` de servidor) lê o arquivo do lado de quem roda o
`psql` — rodar via `docker exec supabase-db psql` faria o `\copy` procurar o arquivo **dentro**
do container, onde ele não existe. Resolvido conectando direto do **host WSL** (que já
monta `C:\` em `/mnt/c/...`) pra porta exposta do container (`localhost:55432`, mapeamento já
existente `5432/tcp -> 0.0.0.0:55432`) — evita duplicar um arquivo de 2,79 GB pra dentro do
container via `docker cp`. `psql` não vinha instalado no WSL; instalado via
`apt-get install postgresql-client` (como root, sem senha — mesmo mecanismo do `/infra`).

### Resultado

`COPY 4120347` em **8min49s**. Verificado depois:

- `COUNT(*) = 4.120.347`, todos com `empresa_id` = a única empresa (correto).
- `geom`/`geom_area` sem nenhum `NULL` (toda linha tinha as duas geometrias).
- `ST_X(geom)`/`ST_Y(geom)` batendo exatamente com as colunas `longitude`/`latitude` de texto —
  confirma orientação correta (X=longitude, Y=latitude, sem troca) e que a conversão preservou
  o dado fielmente.
- RLS testado como `app_user` de verdade (não `ROOT`, não dono da tabela): sem contexto de
  tenant → 0 linhas; com `empresa_id` certo → 4.120.347; com `empresa_id` de outra empresa → 0.
  Fail-closed confirmado no dado real, não só na tabela vazia do Adendo 1.
- Tamanho em disco: 2.370 MB (`pg_total_relation_size`, tabela + índices, incluindo os dois
  GIST).

Índices GIST criados **antes** do import (não depois) — o load já manteve os índices durante
a carga, em vez de precisar reconstruir 4M+ entradas de uma vez no fim. Pra um volume desse
tamanho, criar depois costuma ser mais rápido (evita manutenção de índice por linha durante o
load), mas não chegou a ser um problema aqui (~9min pro total). Vale considerar a ordem
inversa (`COPY` primeiro, índice depois) se um import futuro for significativamente maior.
